01 /

先确定“最优”针对什么

主推荐：TypeScript 插件 + IndexedDB 本地状态 + 独立同步 API + Go 服务 + PostgreSQL 元数据 + 不可变密文对象存储。

选择依据按优先级排列：保护未同步修改 → 可恢复性 → 电脑与手机行为一致 → 隐私边界清晰 → 同步效率 → 维护与部署体验。不把少写代码作为决策依据，也不把引入更多基础设施等同于更优。

SOURCE OF TRUTH
本地优先

用户内容保存在 Vault。服务失联不阻止编辑；提交确认只表示该快照已远端持久化。

CONSISTENCY MODEL
版本驱动的最终一致

单文件因果关系与命名空间更新有明确事务边界。并发分支被保存，客户端完成合并。

PRIVACY MODEL
客户端持有密钥

服务端看不到正文、附件和真实路径；协议标识、版本关系与流量信息仍可见。

为什么主推荐 PostgreSQL：这里优先选择显式事务、行锁、约束和成熟恢复工具，让文件版本、路径占用、幂等结果、对象引用与变更日志在同一提交中成立。SQLite 同样能正确实现个人同步，它是有效的轻部署备选，而不是“可靠性较差的数据库”。[4][5]

已确认：个人多设备、整库同步、自建服务器、端到端加密。不纳入当前产品目标：多人协作、公开分享、移动系统关闭应用后的持续同步。尚未确认的库大小、附件分布与网络条件，作为后续实测输入，不预设容量或速度承诺。

02 /

除了 PouchDB + CouchDB，还能怎么做

需要分别选择本地状态存储、远端数据库和同步协议。数据库的 ACID 事务不能自动解决跨设备同步；换成 PostgreSQL，也仍然需要版本、冲突、幂等、删除与恢复规则。

方案真正提供的能力仍需自行解决本项目判断
PouchDB + CouchDB成熟的文档增量复制、修订树和复制检查点文件映射、分块、配置、加密、冲突界面与恢复可选。适合数据库复制模型；独立文件协议不必继承其修订格式。[1]
独立文件协议 + PostgreSQL事务化版本与路径协调、条件提交、显式历史和变更日志客户端同步状态机、失败恢复、传输与合并主推荐 协议围绕 Vault 文件设计，独立控制完整行为。
独立文件协议 + SQLite单机事务存储，WAL 支持读写并行、同一时刻一个写者与上项相同；额外限定单机元数据服务部署个人单实例的良好备选。轻部署优先时可选，协议无需改变。[4]
RxDB + 自建 HTTP 后端检查点拉取、条件推送、重连与客户端冲突处理框架文件系统适配、密文对象、历史、命名空间、保留双方的冲突策略适合结构化本地数据库应用。默认冲突策略会采用服务端状态，不能原样用于本需求。[6]
WebDAV / S3 直接同步文件或对象读写；部分条件写入与版本功能跨对象事务、完整变更日志、离线删除、并发重命名与加密索引适合通用存储兼容目标；单独作为协调层，正确性边界更复杂。S3 可作为密文对象后端。[7]
Yjs / Automerge 等 CRDT结构化协作状态与操作合并；Yjs 更新可乱序、重复交换Markdown 文件双向映射、外部编辑导入、附件、路径和配置同步当前不作为整库同步基础。将来可作为单篇笔记的协作能力。[8]
Git / 系统级目录同步版本控制或文件同步机制，可参考其历史与扫描思想统一移动插件体验、端到端加密与设备配置语义不作为本插件主协议；可用于用户额外备份，避免两个引擎同时写同一库。

选择 PostgreSQL，是为了清楚的协调与恢复边界。

使用关系约束管理文件身份、位置、版本头和对象引用；短事务内完成条件提交和事件追加。服务端不读明文。对象字节独立保存，不把大附件塞进数据库。

成本：增加数据库进程、迁移与备份运维。收益并非当前个人场景“需要高并发”，而是复杂状态有可验证约束、备份恢复工具完整，后续扩展不改变文件协议。

如果运行环境强调单二进制，SQLite 是合理选择。

维持相同协议与数据语义，使用本地磁盘、WAL、短写事务和明确的忙等待策略。将写提交串行化；不要把 WAL 数据库放在网络文件系统上，也不要让多个主机直接共享数据库文件。

只正式支持一种数据库作为首个发布目标。以后通过存储适配与同一合同测试增加另一种，避免一开始维护两套行为。SQLite 的恢复方案需使用备份 API 或协调快照，不能随意复制活动中的主文件。[18]

CouchDB 的优势是现成的文档复制，不是直接理解文件。

如果产品决定沿用多主数据库复制与 LiveSync 数据格式，它仍是最自然的选择。换后端后继续仿造 CouchDB 的全部协议，反而会同时承担两套复杂度。

对于当前独立实现，参考其因果版本和检查点思想即可。CouchDB 修订号也不等于永久历史，复制通常不会带走所有旧修订的内容。[2]

客户端保存用户意图

监听变化、启动核对、生成不可变快照、记录正在编辑的准确版本、执行三方合并、校验和应用远端内容。Vault 是日常编辑界面，不让“数据库里的最新版本”直接覆盖用户正在写的文件。

服务器协调可验证的提交

识别文件 ID 与不透明路径键，校验版本前提、路径唯一性、对象完整性、操作幂等。服务器保存冲突分支，但无法合并加密正文。

稳定随机 file_id 表示文件身份；内容修订 表示文件字节与删除意图；位置记录 表示目录路径。三者分开后，“电脑重命名、手机修改正文”通常能合并为新位置上的新内容，而不必人为制造同一文件的两个副本。

实现栈建议：插件 TypeScript + Obsidian API + Dexie；服务器 Go + pgx；OpenAPI / JSON Schema 生成类型与协议校验。传输采用 HTTP，WebSocket 只发送“有新事件”的通知，断开不影响最终正确性。[3][9][20]

04 /

数据库存状态，对象存内容

服务器使用 PostgreSQL 作为协调账本。正文和附件先在客户端加密，再进入不可变 Blob Store。个人服务器默认使用本地持久化磁盘；需要独立存储或多实例时接入具备明确条件写与耐久语义的 S3 后端。

服务端实体主要字段 / 约束职责
vaults / devicesvault_id、epoch、next_seq、schema_version；设备令牌摘要、状态与进度隔离库、控制接入、序列化短提交；服务恢复后更换 epoch
files / file_heads随机 file_id、entry_kind（文件 / 目录）；当前修订 ID 集合；唯一 (vault_id, file_id, revision_id)稳定身份与未解决分支。多个头表示冲突，不根据时间静默选胜者
revisions / revision_parentsrevision_id、file_id、parents、kind、encrypted_manifest、key_epoch不可变内容快照与因果关系；删除也是修订，合并可引用多个父版本
locations / namespacefile_id、location_rev、path_key、encrypted_path；唯一 (vault_id, path_key)独立管理路径。HMAC 路径键保证同路径不会被两份文件静默占用
objects / revision_objectsblob_id、ciphertext_sha256、字节数、完成状态、租约；修订引用关系校验对象已完整落盘，并为历史保留和垃圾回收提供显式引用
changes / operations每库 seq、batch_id、密文封装；唯一 (vault_id, device_id, op_id) + 请求摘要增量拉取、组提交与幂等。相同操作 ID、不同请求内容必须拒绝
snapshots / retention_pinssnapshot_id、boundary_seq、冻结的条目引用、过期时间；保留根一致的首次下载 / 恢复快照，保护正在使用的历史与对象

名称是逻辑实体，不是最终建表脚本。服务端可见路径等价关系、版本父子关系、删除类型、对象关联与密文长度；真实路径、内容、明文指纹和配置属性均在密文中。客户端生成的身份、父修订和对象引用等解释字段绑定到认证加密；服务器分配的 seq / epoch 在连接与恢复协议中检查，不声称内容加密能认证服务器的全局排序。

零字节文件和空目录也保存显式条目：空内容不等于删除，目录不依赖子文件才存在。目录位置、删除与冲突遵循同一身份规则。默认不跟随符号链接读取库外内容；发现链接时列出未同步项并说明导入方式，不显示虚假的整库完成。

客户端：IndexedDB + Dexie

保存文件与身份映射、已展示的内容修订、位置版本、明文内容指纹、不可变 outbox、待应用 inbox、两个同步游标和冲突状态。IndexedDB 事务负责本地状态提交；网络、加密和文件 I/O 在事务之外完成，再用短事务登记结果。[9]

客户端：可恢复的加密暂存

上传快照、下载暂存和覆盖前副本放在配置目录的独立 <plugin-id>-local/<device_id>/ 下，由 Adapter 访问，始终排除出同步；不放在升级可能替换的插件程序目录里。大字节不长期复制进 IndexedDB。任务登记暂存校验值；重启恢复时不凭“文件存在”认定写入完整。

本地数据库丢失的安全降级：Vault 内容仍在，但原有删除意图和分支来源可能不可恢复。此时暂停自动删除与覆盖，以“已有本地内容的新设备”重新核对，导入可验证的暂存草稿。不能假设重新扫描就能还原所有历史意图。

小文件整块，大文件按内容切块

小笔记和配置使用单块快照；大附件采用内容定义分块（FastCDC 候选），支持块级重试和库内复用。首轮实测参数建议：小文件阈值 1 MiB；大文件平均 1 MiB、最小 256 KiB、最大 4 MiB。它们是调优起点，不是已验证最优值。[14]

分块在加密前进行。逻辑块键由专用密钥对内容生成 HMAC，避免暴露公开的明文哈希；物理 blob_id 与逻辑块键分离。相同内容并发上传产生不同密文时，通过条件登记选择可验证对象，客户端校验后复用；已有物理对象永不原地覆盖。只在同一库与密钥时期内去重，不做跨用户去重。

去重会暴露同库块的重复关系。可以提供隐私优先的随机块标识策略；其代价是更高带宽与存储。分块算法不参与版本正确性，同一库允许读取不同分块格式；每份 manifest 明确标记格式。

05 /

同步协议：持久化，再发布

一次上传成功，应当意味着“这份不可变快照和它的引用已耐久保存”；一次本机同步完成，还必须意味着“下载已验证并安全应用到 Vault”。

恢复本地任务并建立连接身份

校验 vault_id、epoch、协议版本与功能集合。先检查未完成应用和 outbox，再启动扫描；新旧 epoch 不匹配进入恢复核对，不直接续用旧游标。

记录本地修改的准确基线

保存正在编辑的 displayed_revision 和 location_rev。生成内容快照后固定 op_id；后续继续编辑产生新的任务，不更换旧任务的上传字节。

拉取增量，先登记再应用

HTTP 按 seq 拉取；在一个本地事务中登记收到的封装、应用任务和 received_cursor。后台验证解密并处理文件，单独推进连续的 applied_cursor。

上传缺少的不可变密文对象

分块上传、长度与密文校验、完成确认。服务器对象写入和必要的 fsync 完成后才标记 finalized；已确认对象由上传租约保护。

事务化提交版本 / 位置变更

校验鉴权、操作摘要、父修订、路径占用与全部 finalized 对象；在同一 SQL 事务里更新状态、引用、幂等结果和变更日志。字节传输不占用此事务。

保存结果，重新核对本地内容

收到提交回执后标记该快照已上传。只有当前文件仍匹配快照，才将其标为该版本；否则它是下一份未同步修改，不能把“已上传”误用到更新的字节。

两处容易被忽略的原子性

事件序号必须与提交顺序一致

不能直接把 PostgreSQL 的全局 sequence 当作无缺口同步游标：先取号的事务可能后提交。每库在短提交事务中锁住 vault 状态行，分配连续 seq 并追加日志，锁一直持有到事务结束。上传可并行，元数据发布按库串行。

数据库事务不能覆盖文件系统

服务端先耐久保存不可变对象，再提交引用；客户端先登记应用任务，再写 Vault，最后确认状态。崩溃后根据内容校验和任务阶段恢复。不存在一个同时原子提交 PostgreSQL、磁盘和手机 Vault 的大事务。

首次连接、分页快照与持续变化如何衔接

空库使用快照 B 下载当前文件、位置和必要冲突版本，再从 B 拉取增量。已有本地库先扫描和保存草稿，再做路径与内容比较；缺少共同基线时不传播删除、不猜测空文件祖先。

快照创建时冻结条目 / 修订引用，并设置保留租约。分页请求读取同一份物化快照；随后发生的变化留在 B 之后的日志。不能分页读取不断变化的“当前表”，同时声称得到一个一致快照。

为什么不直接使用时间戳或普通 If-Match 完成整个协议

时间只用于展示和扫描优化。内容变化由内容指纹确认；覆盖前提由修订身份、位置版本和已观察头集合确认。HTTP 条件请求可承载单资源 CAS，但跨文件路径更新、对象引用和幂等回执仍需应用层事务。[10]

06 /

冲突是一种被保存的状态

每份修订有明确父版本。正常编辑扩展设备实际展示的修订；服务器发现父版本已不是当前头时，保存为并发分支并发布冲突事件，不以“最后收到”为理由覆盖。解决冲突时提交引用已观察分支的合并修订，条件检查避免误删后来出现的分支。

已确认的产品规则：重叠修改必须由用户选择。发生内容重叠时，停止该文件的自动覆盖，保存电脑与手机双方版本。不能根据修改时间、设备优先级、上传顺序或超时默认选择某一方；其他文件继续正常同步。

情形处理规则对用户的结果
两端修改后字节相同验证字节与修订关系，生成收敛记录自动完成；不生成重复副本
Markdown 有共同祖先，改动不重叠保守三方合并；合并结果成为新修订，保留父版本自动合并，可在历史中查看和撤销
同段落修改 / 祖先不可用保存双方，展示差异；必须由用户明确选择都保留、电脑版本或手机版本，也可手动合并不自动决定主版本；暂不处理时保留双方，持续显示待处理状态
图片、PDF 或其他附件冲突二进制不做语义合并，也不按修改时间选胜者预览 / 下载双方版本，选择或保留副本
删除 + 未修改应用逻辑删除；本地移入可恢复回收位置其他设备删除文件，历史仍可恢复
删除 + 并发修改删除修订与内容修订并存；保护正在显示的本地修改明确选择删除、恢复修改，或导出修改再删除
重命名 + 正文修改位置版本和内容版本分别推进，稳定 file_id 关联修改出现在新路径；无需复制整份附件
两端重命名 / 目标路径被占用位置 CAS 失败并保存候选意图；不删除源，不猜目标用户选择最终位置，或调整冲突文件名

配置里的 JSON 也不能一律做键级合并。已知、稳定且可验证的设置模式可以对互不重叠字段合并；数组默认整体比较，未知插件配置默认保守处理。frontmatter 的格式、注释与列表变化需要文本级保护，避免“合法 JSON / YAML”被误当成语义正确。

冲突选择界面

按实际设备名称标记每份版本，显示修改时间与内容差异；不使用容易混淆的“服务端优先 / 本地优先”。主要操作如下，均需要用户明确确认，没有倒计时或默认覆盖。

用户选择确认前预览结果
都保留显示两份最终文件名，并允许指定哪一份沿用原文件名形成两份独立文件，其他设备同步同一结果，不重复生成副本
使用电脑版本预览所选电脑快照及将被替换的手机内容电脑快照成为统一版本；未选快照按历史保留策略保存

手动合并 / 暂不处理可编辑合并结果，或保留当前编辑界面并稍后处理未确认时双方都在；待处理状态跨重启保留，同一冲突不反复弹窗

第 1 / 4 步
重命名、目录批量操作与跨系统路径规则

路径键采用 HMAC(K_path, canonV1(path))。canonV1 固定分隔符与 Unicode 规范化，并采用不依赖设备区域设置的大小写等价策略；实际路径拼写保存在密文中。大小写冲突、非法路径、保留名和路径穿越在客户端检查，发现冲突时暂停相关文件而不是自动改名或丢弃。

文件夹重命名成为一组位置操作：服务器一次事务检查全部目标并提交，批量事件保持组边界。客户端先准备清单，再逐项应用并记录进度；本地文件系统没有跨文件大事务，所以只承诺可恢复执行，不承诺用户永远看不到中间状态。

应用内 rename 事件可保持身份。应用关闭后，外部工具移动文件通常无法被可靠识别；扫描只能提出候选映射。内容恰好相同不证明是同一文件，模糊情况按创建 / 删除候选保护并提示，不伪造确定的重命名。

“保留双方”怎样避免各设备生成一堆冲突副本

冲突分支使用稳定 revision_id，各设备同步同一冲突实体。用户选择保留双方时，生成稳定的 resolution_op_id 和伴随文件 file_id，通过一组提交创建副本并收敛原文件。重复请求或另一台设备重放只得到同一结果。若冲突集合在审阅期间改变，则重新审阅。

设计采用随机 256 位库主密钥。口令通过 Argon2id 派生封装密钥，保护主密钥包；内容、元数据、路径索引和块标识使用带明确用途的独立派生密钥。改口令只重新封装主密钥，不要求重新加密所有文件。

内容 / 元数据 / 路径 / 块索引

内容加密

候选采用 libsodium.js 的 XChaCha20-Poly1305，逐对象随机 192 位 nonce。块的认证绑定库、密钥时期、用途、blob_id 和逻辑块键，允许跨文件复用；manifest 的认证绑定 file_id、revision_id、父修订、删除类型和有序块引用。位置封装独立绑定位置版本与路径键。[11][12]

口令与设备资源

固定 Argon2id 版本，保存 salt、内存和计算参数。以 64 MiB 作为实测起点，在最低支持手机上测解锁延迟和峰值内存后定发布参数。参数边界要防止异常资源消耗，不静默退回弱 KDF。解锁失败只报错，绝不重新初始化远端。[13]

保护范围服务器能否看到备注
正文、附件、设置属性、真实文件名和目录不能读取仅在客户端解密；明文指纹也不直接上传
随机 file_id、位置键相等关系、版本因果与删除状态可见协调、唯一约束与增量协议所需的控制信息
密文长度、库内重复块关系、设备连接和访问时间可见可通过关闭去重、填充和批量请求降低部分泄露，但有资源代价
本地 Vault 文件本地仍为明文端到端加密不是设备磁盘加密；不能阻止本地恶意插件读取笔记

新设备接入：授权和解锁是两件事

批准设备

首次部署生成一次性管理员接入方式；已有设备或管理端创建短时、单次使用的邀请码，新设备兑换专属随机 API 令牌。令牌在服务端只存摘要，不使用共享管理员密码做日常同步。

解锁库

新设备取得加密密钥包，本地输入库口令；也可导入离线恢复密钥。邀请码不携带明文主密钥。二维码仅作为接入信息载体，不能让服务器获得解密权。

选择初始化方式

空库下载；已有本地文件则预览合并与冲突。成功校验密钥和库身份后才能创建 outbox、接受删除或自动应用配置。

恢复与撤销：生成可校验的离线恢复密钥，提醒用户保存。重置服务器登录凭据不能恢复加密口令。撤销设备令牌立即阻止 API 访问，但已下载的内容和旧密钥无法追回；完整的加密撤销需要新的密钥时期并重加密需要保护的数据。

用户已确认填写 server 地址与同步密钥，保存并测试连通性及密钥后自动连接；已保存的密钥可留空复用。日常只提供暂停/恢复同步，暂停保留配置与密钥，重开后仍暂停，恢复不重输密钥；不提供记住解锁开关或锁定入口。当前 Mac 已验证设备保护的解锁材料恢复；不把口令或明文密钥写进插件 data.json。Windows/Linux 与 iPhone 安全存储仍待实测。加密真实性不能独自保证恶意服务器不会隐瞒或回放历史；设备保存最高已见进度和版本锚点以检测已知回退，完整抗分叉保证需额外的透明日志 / 设备交叉验证，不在本版承诺范围。

整库同步，也尊重设备差异

同步范围涵盖笔记、附件、插件、主题和配置；每类文件都遵循相同的身份、版本和加密规则。配置有单独的应用策略，避免在插件正在运行时替换它自己的代码或把桌面布局灌进手机。

数据类别默认策略应用方式
Markdown、Canvas、其他用户文件和附件全量纳入；文件类型不作为静默忽略理由普通文件通过 Vault API；支持文本三方比较和二进制双方保留
主题、CSS snippets、快捷键与可共享设置共享，可按类别关闭；预览首次配置同步方向配置目录通过 Vault.configDir 发现、Adapter 访问；必要时提示重载
第三方插件程序与设置纳入共享；允许逐插件设为设备独立程序先暂存，再在安全重载边界应用；桌面专用插件保持其平台限制
workspace、workspace-mobile、设备临时状态设备独立可做设备专属备份，但不跨设备覆盖当前布局

令牌、密钥缓存、outbox、inbox、暂存、索引、回收区硬性排除禁止同步自身状态；未知插件凭据提示按插件审阅，不承诺自动识别所有秘密

“整库”在这里表示用户数据及可共享配置完整覆盖，不包含本机运行日志、缓存和同步引擎的内部状态。排除规则在设置中可查看；不能用隐藏的文件大小过滤，让用户误以为库已完整同步。[15]

移动端必须优先验证的三件事

源文件读写的真实内存

网络分块不等于源文件流式读取。若公开 Adapter API 只能返回整文件 ArrayBuffer，峰值内存仍受附件大小影响。大附件能力必须先在 iOS / Android 真机验证，再公布支持范围；不能凭桌面 Worker 测试宣称任意大文件可用。

应用生命周期

启动、回到前台、网络恢复时补拉。后台暂停前尽力持久化任务，恢复后继续，不依赖系统给足收尾时间。手机被关闭 / 挂起后，不承诺持续运行同步。

文本覆盖的安全入口

普通文本优先用 Vault.process 在当前内容回调里检查预期旧字节。二进制和隐藏配置使用临写复核、回滚副本与应用任务恢复；外部写入的竞争不宣称由插件锁完全消除。[15]

自动同步采用事件触发 + 短暂合批 + 前台定期核对。WebSocket 通知丢失时仍能补拉；文件监听漏事件时启动扫描补偿。mtime 和 size 只用于候选筛选，不能证明内容未变；还需要周期性内容校验与用户可触发的全库核对。

同一个库若存在多个活动插件实例，通过 IndexedDB 租约 / 领导者机制选一个执行同步；租约失效后另一实例接管。租约只协调本地引擎，不锁住 Obsidian 编辑器或外部进程。用户界面分别显示：待上传、待下载 / 应用、冲突、失败、最后核对时间；只有任务结清、无错误且无未解决冲突，才显示“本机同步完成”。有冲突时显示“传输完成 · 需处理冲突”，不宣称整库已经收敛。

09 /

恢复能力从数据结构里长出来

历史是显式的不可变修订

建议默认保留 90 天已接受内容修订，可按空间和需求调整。当前版本、未解决冲突、合并需要的祖先和活动任务依赖不受普通历史到期影响。恢复旧版本生成新的修订，绝不把当前指针直接回拨到过去。

删除的“证据”长期保存

轻量墓碑 / 文件生命周期记录长期保留，避免旧设备把删除误解为“服务器从来没有这个文件”。大内容可按历史策略到期；旧设备拿不到祖先时进入保守核对，仍保留本地修改。

对象垃圾回收采用“标记 → 宽限 → 再检查 → 清除”

保留根包括：当前所有版本头、保留期内历史、未解决冲突及其必要祖先、快照、上传 / 应用租约、活动设备声明的待处理基线、备份与 PITR 所需对象。标记后等待宽限期，删除前在短事务内重新检查根与租约，再禁止新的引用。单纯看引用计数为零、设备游标已确认或文件已删除，都不够安全。

长期离线设备的租约可以过期，但重新接入必须完整核对，不能直接按过期索引传播删除。容量不足时显式暂停新上传并提示，不静默清理冲突或缩短已承诺的历史。

故障恢复行为需要保持的事实
对象上传完成，版本尚未提交继续提交；未引用对象由租约保护，超期可清理不让半上传对象进入可见修订
SQL 提交完成，响应丢失同一 op_id 查询 / 重试，返回原结果不重复创建版本或冲突副本
远端事件已收到，尚未写 Vaultinbox 任务重启后继续received_cursor 与任务一起提交，应用进度另记
写入 Vault 完成，确认尚未保存比较目标字节；相同则补确认，不同则保护当前内容不能盲目重放覆盖操作
本地数据库被清除导入可验证暂存，按已有内容新设备重新核对不自动推断删除、修订祖先或重命名
服务器恢复旧备份服务更换 epoch，客户端停止旧游标路径并重建比较恢复后的远端不自动成为所有设备的权威

数据库备份和密文对象必须形成同一恢复点

个人部署提供一键生成一致备份：暂停元数据发布和 GC，创建数据库一致快照，记录对应 seq、对象清单与协议版本，然后复制 / 归档清单中的不可变对象。对象复制期间可以恢复新提交，但必须保持快照引用的对象不被删除。备份完成后验证清单和摘要，并做实际还原演练。

PostgreSQL 可扩展连续 WAL 归档与 PITR；对象归档的保留范围也必须覆盖最早允许恢复的时间。只有数据库能回到过去、对应密文对象却已被清理，不能称为整库 PITR。初始发布必须包含完整备份 / 还原命令；可选连续归档在恢复演练通过后开放。[19]

部署形态：反向代理提供 HTTPS，Go 服务和 PostgreSQL 使用内部网络；数据库不直接暴露公网。持久化卷分别保存数据库、对象和备份。管理界面只显示设备、空间、任务和健康状态，默认没有明文文件浏览能力。版本升级前备份，协议迁移先检查全部设备能力。

向 LiveSync 学什么，自己决定什么

这一版不是 LiveSync 的换皮，也不要求与它的数据库或密文格式兼容。独立协议意味着可以更改身份、位置、历史和恢复模型；同时也必须独立证明正确性。迁移优先通过正常 Vault 文件导入，不直接修改旧 CouchDB 文档。

上游经验本设计如何使用不直接沿用的部分
准确记录文件展示版本保留同样的因果原则，作为内容编辑基线不依赖 CouchDB winner 或修订代数判断新旧
缺块等待和到达乱序服务端提交前校验依赖，客户端仍做验证、补取和恢复不继承多远端 / 在线按需块组合的设置矩阵
分块、内容复用与删除修订使用独立对象与显式生命周期版本不沿用 Eden、旧块格式、旧加密版本和路径派生文件身份
事件队列 + 扫描补偿持久化任务、处理阶段与启动复核，作为必要机制不声称队列快照就是完整文件日志
配置分开处理、设备状态排除一套同步分类，独立应用策略不同时提供两套可重叠的配置管理入口
真实故障和多设备测试复用测试思想与边界场景，独立构造合同测试不以单元测试通过代替真机与真实 Obsidian 验证

上游 Commonlib 仍明确标记 pre-1.0，完整客户端工厂尚未稳定提供。因此本设计不建立在“接入一个现成 SDK 就得到完整同步”这一假设上。若实际复制上游代码或测试，需保留相应版权与许可；参考机制并不意味着继承其数据格式。[16][17]
