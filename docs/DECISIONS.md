## 冲突规则的具体合同

- 选择前显示实际设备名称、内容差异与所审阅的快照。
- “都保留”预览两份最终文件名，并明确哪份沿用原路径；其他设备同步同一解决结果。
- “使用某一方”只采用用户看到的准确快照；未选快照按历史策略保留。
- 暂不处理时保留双方与待处理状态；该文件停止自动覆盖，其他文件继续同步。
- 审阅期间出现新修订，旧选择不得丢弃未展示分支，需要更新比较。
- 用户继续编辑时记录准确的版本来源；不能因为数据库存在另一个更新版本，就偷换编辑祖先。

## 技术架构

| 层 | 当前设计推荐 | 选择理由 / 限制 |
| --- | --- | --- |
| 插件 | TypeScript + Obsidian API | 共享电脑与手机实现；核心不依赖 Node.js / Electron |
| 本地状态 | IndexedDB + Dexie | 本地事务与可恢复任务；网络、文件 I/O 与加密不放进长事务 |
| 暂存 | 配置目录内独立的设备加密暂存 | 与插件升级目录分离，不参与共享同步 |
| 服务端 | Go + pgx | 独立服务、明确协议与持久化边界 |
| 元数据 | PostgreSQL | 事务、约束、行锁、历史与恢复工具；SQLite 为有效轻部署备选 |
| 内容 | 不可变密文对象 | 大字节与 SQL 分离；先耐久对象，再提交引用 |
| 同步 | 独立文件协议 + 有序事件日志 | file_id、内容修订和位置版本分离；HTTP 是补齐依据，WS 只通知 |
| 加密候选 | 随机主密钥 + Argon2id + 用途隔离派生 + XChaCha20-Poly1305 | 需固定协议向量、移动资源实测和安全审查 |
| 分块候选 | 小文件整块，大文件 FastCDC | 先测手机读写 API，再确定阈值与参数；不保证任意大附件 |

上述技术不是用户逐项批准的最终栈。SQLite 的轻部署优势、PostgreSQL 的协调 / 恢复能力、现成复制引擎与自建协议的责任均已在 HTML 比较。调整推荐需要记录依据，而不是仅因为某一方案更容易写。

## 核心不变量

1. 已接受版本的全部内容引用耐久存在且可校验。
2. 同一 op_id 与请求摘要绑定；重试不产生重复版本或副本。
3. received_cursor 与待应用任务一起持久化；applied_cursor 单独推进。
4. 当前文件不匹配已上传快照时，不能将新字节标成已同步。
5. 扫描错误和访问失败不是删除证据。
6. 重命名目标失败不删除源；客户端多文件操作按日志恢复，不声称跨文件事务。
7. 冲突、历史、活动任务、快照和备份依赖在 GC 中得到保护。
8. 服务器恢复旧备份更换 epoch；客户端重新核对，不自动服从回退的远端。
9. 错误密钥或未知协议只阻止操作，不触发远端初始化 / 重建。
10. 未解决冲突显示“需处理”，不能报告整库已收敛。

## 实现前需验证

- 手机公开文件 API 的大附件读写和峰值内存。
- IndexedDB 丢失后的保守重接入，以及加密暂存的可恢复边界。
- Worker / WASM、KDF 内存与解锁延迟。
- 跨平台安全密钥存储与“记住解锁”的实际能力。
- Unicode、大小写、保留名、目录重命名和外部文件操作。
- 三方合并与配置应用的准确合同。
- 数据库和对象联合备份 / 还原，包括 PITR 对象保留。
