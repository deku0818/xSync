# 电脑端自动解锁与实时同步验收

日期：2026-10-14（Asia/Shanghai）。开发插件版本 0.0.3；macOS 27.0.1，Obsidian 1.14.4，安装程序 1.8.9；同机 A/B 独立测试库与真实 IndexedDB / Vault API。后端仍是本项目的 Go 服务与 Docker PostgreSQL。

用户已确认：首次配置设备后记住解锁，日常打开库自动解锁、补齐和近实时同步；不要求重复输入口令或点击同步。主动锁定、凭据不可用等情况下才重新解锁。iPhone 之后验证。

## 已实现的行为

- 电脑首次解锁后，默认记住当前设备；后续插件重载或测试库窗口重开，从设备保护的材料恢复，不保存库口令。
- 文件创建、修改、删除、重命名触发自动核对。350 ms 合批，持续事件最多等待约 2 秒；同一引擎的同步、位置意图和显式解决串行执行。
- 服务端 SQL 提交后发布 WebSocket 提示，客户端按 HTTP 日志拉取、验证并应用。提示不携带文件内容，不直接推进游标。
- 事件断开按 1/2/4…30 秒退避重连；启动、恢复网络、窗口回到前台触发补齐，另有 30 秒周期核对补漏。
- 重叠修改只阻止相关文件覆盖。其他文件继续自动传输；比较页遇到新修订自动刷新并清除旧选择，确认前须重新选择准确快照。
- 设置可以暂停/恢复自动同步、关闭记住解锁，或主动“锁定并忘记本机解锁”；主动锁定持久化禁用标记，不会在下一次启动偷偷恢复。

“立即核对”保留为主动检查入口，正常流程不需要点击。插件升级会把旧版默认手动测试设置迁移为自动；新设置格式中明确暂停的选择会保留。

## 解锁材料保护

当前 Mac 使用 Obsidian 随附的 `@electron/remote` 访问 Electron `safeStorage`。其 macOS 密钥保护依据是系统 Keychain，见 [Electron 官方存储语义](https://www.electronjs.org/docs/latest/api/safe-storage)。只在桌面适配层加载 Electron / Node Buffer，同步核心不引入它们；构建也检查这一边界。

本机记录在 `<configDir>/obsidian-sync-local/desktop-unlock.json`，文件只有格式、保护器名称和 OS 密文字节。明文材料只在进程内流转，包含恢复用的用途子密钥与远端密钥包锚点，不包含库口令。材料有独立完整性校验，并与库、设备、数据库 ID、服务器地址绑定。客户端恢复后，先校验远端库身份、epoch 和密钥包锚点，再产生上传/应用意图。

不可用、损坏、未知格式或机器/身份不匹配时保留原记录并提示重新解锁，不初始化远端、不降级明文存储。Linux `basic_text` / 未知保护后端会被拒绝。Windows/Linux 只有适配逻辑与组件测试，尚无实际平台验收。

这是对静态解锁记录的设备保护，不是 Vault 磁盘加密，也不隔离同一个 Obsidian 进程中的其他插件。设备 API 令牌仍是开发预置配置，完整凭据管理和正式设备接入界面待做。

## 事件通道

`POST /events/tickets` 使用已有设备鉴权，生成 60 秒、单次使用的票据。WebSocket 固定路径 `/events`，票据通过首帧提交；令牌/票据不放 URL。握手、帧大小、发送时间有界，服务端校验来源，连接有心跳。

通知发生在 SQL 提交之后、回执故障注入之前；提交已耐久但响应丢失时，其他客户端仍可收到提示。通知队列只合并提示，HTTP 日志仍完整。当前通知 Hub 面向单 Go 服务实例，多实例推送协调和完整生产限流仍待做。

Obsidian 原生 HTTP 请求使用 15 秒客户端超时边界；公开 API 无取消接口，底层请求可能晚到，因此依然依靠不可变 outbox / op_id 重试合同保护，不声称超时取消了服务器提交。

## 真实 A/B 验收结果

| 场景 | 实际证据 | 结果 |
| --- | --- | --- |
| 设备保护 | A/B 本机文件均为 `electron-safeStorage:darwin` 密文记录，插件 data.json 只有设置；未写明文库口令/会话密钥 | 通过 |
| 插件重载 | A/B 重载插件后均显示“本机已自动解锁”、事件 connected、待上传/应用/冲突为 0；没有输入口令 | 通过 |
| 测试库窗口重开 | 只关闭 A 测试窗口，从 B 的库选择器重新打开 A；新窗口自动恢复、连接、补齐，没有口令框 | 通过 |
| A → 后台 B | 只编辑/保存 A，不点击核对、不切到 B，监测 B 文件自动收到同一字节 | 通过，观测约 0.815 秒 |
| B → 后台 A | 同样从 B 编辑/保存，A 后台自动收到 | 通过，观测约 0.818 秒 |
| 自动重连/并发 | 停止本项目 Go HTTP 服务，分别在 A/B 保存不同内容，再启动同一服务；没有重新解锁或手动核对，两端自动提交同一准确父版本的两个分支 | 通过 |
| 冲突不覆盖 | 重连后显示需处理、冲突 1，两端原字节保留；没有时间/设备/上传顺序胜者 | 通过 |
| 其他文件继续 | 主文件冲突未处理时编辑独立笔记，B 自动收到 | 通过 |
| 实时更新审阅 | A 先选 A 快照；比较页保持打开时 B 再编辑，A 自动展示最新 B 内容并清除旧选择；直接点确认要求先重新选择 | 通过 |
| 保留双方自动传播 | 重新比较后选 A 沿用原路径，B 最新修订保存为 `自动实时-保留电脑B.md`；B 不点按钮也收到两份 | 通过 |
| 自动保存 | A 粘贴新版“开始使用”说明后，没有按保存/核对；Obsidian 自动保存，B 自动收到 | 通过 |

以上时间从观察到源文件新字节到目标字节相同，包含测试轮询间隔；仅当前同机、少量短笔记样本，不是正式延迟/容量承诺。文件监测在接收端保持后台时完成，之后才切到该窗口查看。

断开测试是开发 HTTP 服务正常停止/重新启动，未停止 Docker PG；不是物理网络丢包或操作系统强杀/断电测试。

最终五份 Markdown 在两端逐字节相同，原文件保留 A 的离线内容，新增副本保留 B 审阅期间的最新内容。两端保持自动同步开启、会话已自动解锁、事件 connected，待上传/应用/冲突均为 0。机器记录见 [验收结果](desktop-auto-results-2026-10-14.json)、[延迟样本](realtime-metrics-2026-10-14.json)。
