# 协议语义模型 v0

状态：2026-10-14，实验性可执行参考模型。已有配套的实验 HTTP 校验、Go/PostgreSQL 服务和客户端，开发步骤见 `docs/testing/desktop.md`；下文的“不实现持久化”等限制专指这个内存参考模型。`src/types.ts` 是内部类型，不是冻结的 HTTP / JSON Schema / 加密格式。`VaultModel` 只有内存状态；没有鉴权、SQL、文件耐久、对象上传、GC 或网络服务。

## 本轮固定的可测试语义

- `fileId`、内容 `revisionId` 和 `location.revision` 独立。模型 ID 由调用者提供可读 fixture；生产 file ID 随机，修订/位置 ID 由请求坐标派生，编码受限。
- 普通编辑只能以一个准确的 `displayedRevision` 为父；父修订必须属于该文件。旧父合法，形成并发分支。普通编辑不能冒充多父解决操作。
- 头集合是因果图的极大节点；新修订只移除自身祖先中的头。删除同样是一份不可变修订，不能压过并发编辑。
- 普通内容修改不更新位置。位置使用 CAS；一个组可原子交换两个已占路径，失败则整个组不发布。位置版本 ID 不可复用，避免 ABA。
- 创建需要显式位置。空文件、空目录、删除分别建模；目录不能携带文件块。
- 解决要求 `observedHeads` 与当前完整头集合相等，集合中不能重复。新分支到来后返回 `REVIEW_STALE`，保留所有历史和当前分支。暂不处理就是不提交解决；不锁住其他文件。
- select / manual / keep-both 都是显式解决意图。keep-both 本轮只支持恰好两个头：调用者提供固定 companion file/revision/location ID、准确来源和重新加密的 manifest，原文件解决和伴随文件创建属于同一组。
- 选择操作记录 `selectedFrom`。服务端无法验证密文代表的明文与用户审阅快照相同；最终客户端必须认证来源并重新加密，因为 manifest 绑定 file/revision/parents。模型只核对对象引用顺序、种类和 keyEpoch，没有实现 AEAD 格式。
- `(deviceId, opId)` 绑定实际规范化请求体。对象键排序，数组顺序保持；重试返回首次回执，换请求拒绝。模型保存完整 canonical body 比较，网络摘要算法尚未冻结，不接收调用者自报摘要作为真值。
- 引用对象必须先声明耐久。`declareDurableObject` 只是测试前提，绝不证明 fsync 或摘要校验已实现。
- 每个成功提交组分配一个连续 seq，事件包含整组操作。失败不取号、不发布、不改变历史。模型用复制后发布表示事务；真实 Go/PostgreSQL 要在每库行锁和同一事务中重做合同测试。
- 快照是冻结拷贝，边界 B 后从 B 拉取增量。日志过期返回 `NEED_SNAPSHOT`；旧 epoch 返回 `EPOCH_CHANGED`；未知协议或必需特性拒绝。没有自动重置库的路径。
- inbox 任务与 received 游标一起登记；完成可乱序，applied 只越过连续已完成组。冲突或失败时不显示完成。

## 有意保守的 v0 限制

墓碑仍保留路径占用；安全释放路径、同路径重新创建和目录整棵操作的合同待后续设计。本轮不允许自动复用删除路径。位置 CAS 失败只返回错误，客户端候选意图的持久化尚未实现。

模型输入是受 TypeScript 检查的内部对象，非不可信 HTTP 入口；不应直接暴露给网络。正式阶段还需运行时 schema、大小/深度限制、opaque ID 编码、设备注册与实际名称、密文认证上下文、能力协商细节和跨语言向量。

尚未实现文本差异、冲突 UI、三方自动合并、outbox、Vault 应用日志、幂等结果保留期限、历史/对象回收、授权撤销及真实备份恢复。`InboxModel` 的复制发布不是 IndexedDB 持久化实现；探针的 Dexie 事务只验证底层能力。

## 如何验证

`npm test` 包含定向场景及 fast-check 随机历史。图头 oracle 独立从父关系计算极大节点，覆盖 2–5 个设备标识、离线旧父、删除和重试；固定种子便于重现。失败时保留 fast-check 的 seed/path，再缩减为回归场景。通过这些测试只说明所覆盖的模型性质，没有证明生产实现或所有协议性质。

Go + 真实 Docker PostgreSQL / 不可变对象后端已有 8 项合同测试，客户端有 8 项双客户端集成；完整随机历史的跨实现对照、全部持久化边界进程强杀仍待完成。


## 0.0.6 本机范围与独立接入

规则在每个客户端独立生效，排除保留 localFile/outbox/apply journal，不产生删除。received 游标与远端元数据/inbox 一起持久化；兼容字段 applied 表示本机当前范围已应用或按规则明确跳过的日志边界，不表示所有文件均已写入 Vault。跳过项有本机状态，远端文件/修订继续保留；规则改变后扫描全部已接收远端状态补齐，不依赖重放旧游标。UI 只报告“所选范围”，不宣称整库收敛。

branch 操作向既有文件加入无父的独立修订，用于没有可证明祖先的同路径初始内容，保留既有头。明确被服务端以 PATH_OCCUPIED 拒绝的单文件 create 可在完整归档旧 intent/身份/journal 后重新核对；精确相同字节接入已知修订，否则保留独立分支。复杂移动或未知提交结果不推断修复。resolve 包含 expectedLocation 时同时对位置修订作 CAS，正文头未变但发生重命名也会拒绝过期决定。

## 元数据压缩前置合同（3A，工作区尚未发布）

内存模型仍保留完整图；3A 当时服务端尚未裁剪修订，现行生产 3B 见下一节。新增 `metadata-anchors-v1` 外层信封，原 `Commit` 正文保持不变；`metadata.ts` 定义已接受基线凭据、每设备请求流坐标和提交结果。请求序号用于回执回收和重放隔离，不参与因果或冲突选择。

基线凭据绑定 vault/epoch/file/revision、原修订规范摘要和签发时序号。服务端使用独立持久 HMAC 密钥认证；客户端验证原修订密文清单和凭据身份/摘要。编辑仍以实际展示修订为父，不能把凭据的签发时序号当成编辑顺序。摘要为 SHA-256：JSON 对象键排序、数组顺序保持、Go JSON 的 HTML/U+2028/U+2029 转义；MAC 绑定实现中的固定域和字段顺序，不接收客户端自报摘要作为真值。

同一设备的流/序号绑定准确请求摘要与原结果，重试返回原结果。客户端保存结果、待发送确认和移除 outbox 必须同一事务；服务器只在确认后释放跟踪结果副本，并以连续前缀加稀疏区间拒绝退休序号。失败或排除的空洞不因后续成功而退休。原 `operations` 成功回执在 3A 中仍保留，旧提交入口仍开放。服务端/本机计数回退需要恢复核对，不自动换坐标或改写旧请求。

生产提交同时对照完整图与独立的直接父版本头投影；`tests/protocol/head-shadow.test.ts` 用完整图极大节点 oracle 检查投影语义。影子对照是 3B 压缩的前提；实际删除/检查点已由下一节扩展，对象格式与身份回收已由 3C 扩展，见下文和 DECISIONS。

## 当前头协议与压缩（3B，工作区尚未发布）

`compact-heads-v1` 在 3A 上加入独立检查点和当前头快照。普通编辑从当前头集合移除准确展示父 ID 后追加新 ID，旧的已接受父仍合法；解决必须 CAS 完整当前头及位置。生产客户端/服务端都不递归依赖父修订正文，原修订的 parents/selectedFrom 认证字符串保持不变。完整图参考模型仍保留作独立 oracle，不能把它的无 GC 限制当成生产状态。

新 ID 编码为 op=`q_<stream>_<number>`、revision/location=`m_<stream>_<number>_<role>_<action-index>`，角色 r/l/rc/lc 分开。file ID 保持独立。坐标退休后不重放，换坐标不能复用旧身份。升级前随机 ID 队列原样登记一次；旧接受索引和旧成功回执用于准确基线/结果恢复，未知旧意图保留并核对。该迁移边界不是用户历史版本或回收站。

快照包含所有文件身份、当前头完整修订及一一对应凭据（空库凭据可省略），checkpoint 不得超过 boundary；客户端在同一事务保存凭据/投影/游标。服务端保留日志产生修订和有效冻结头直到相应保护结束，未确认结果自含完整修订；本机只保留展示基线与持久工作引用。3C 已回收新格式对象身份，旧格式随机身份摘要仍保留。具体兼容、限额和清理不变量见 DECISIONS。

## 对象格式与回收（3C，工作区尚未发布）

`objects.ts` 定义 `addressed-objects-v1` 与对象 ID：v0 为原 64 位十六进制随机值；v1 为 `c_<64 位 SHA256>`，哈希覆盖实际完整密文字节。v1 envelope.v=1，XChaCha20-Poly1305 的 AAD 为 object-v1/vaultId/keyEpoch，不包含尚未生成的密文哈希；随机 nonce 保留，manifest 认证准确对象列表。v0 envelope/AAD 不改，读取兼容，新捕获只写 v1；不能通过换前缀把 v0 提升为 v1。

HTTP 同步必须携带对象能力头，原 Commit 仍不重写。compact 模式的旧随机对象新上传以独立的一次设备登记包限定，允许 3B 已迁移后的原队列继续；未知旧意图保留并核对。schema v7 的本机登记状态与 PG 成功摘要处理丢失响应，既有旧身份保持不可变摘要。

新对象的公开 ID 与随机物理 storage_token 分开，读/快照、上传尝试和删除任务都绑定物理标识。内容删除并同步目录后，确认事务可以释放新身份/非头派生边；老任务不能影响新标识。上传必须在创建文件前复查有效登记，临时链接的耐久删除先于释放数据库恢复登记。头 JSON 与有效保护决定保留，不依赖历史修订或派生索引完整性。旧格式身份、旧接受证据、删除/撤销身份仍是迁移/恢复成本，不属于用户历史功能。


## 设备连续性（工作区尚未发布）

强制 `device-continuity-v1` 和 handshake 的 `continuity: true`。每设备一个随机 64 字符十六进制标记，受保护请求通过 `X-Sync-Continuity-From/Next` 与其数据事务一起 CAS，成功响应包含 `X-Sync-Continuity-Token`；本机先持久化 pending，确认后才接受数据。接收日志、提交、基线认证和冻结快照创建/复用均受保护。其他设备不推进此标记，故全局 seq 追平不能掩盖已见数据库的回退。

超时未确认的 From/Next 通过 `POST /metadata/continuity/fence` CAS 到同一个 Next，再持久化确认；迟到原请求从旧 From 提交必须失败。若原请求先完成则读取相同 Next；未知标记要求核对，不自动复位。只读视图允许显式检查而不推进标记，不能提交或用于同步引擎自动应用。升级前准确基线逐一认证，全部完成才退出 bootstrap；空旧队列可读取已有迁移完成状态，不改变原登记摘要。本机制无历史链，不提供历史版本或回收站。
